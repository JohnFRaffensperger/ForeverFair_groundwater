LEGACY DJANGO BID-PROCESSING REVIEW (source: C:\Users\johnr\Documents\Work documents\2 Research\Water\Programming\Django)
Date reviewed: 2026-04-30
--------------------------------------------------------------------------------

1. Starting with an empty bids table, how are initial bids established?
   - In this legacy code, initial bids are established by creating BidSet rows and Bid rows.
   - There is no default-bid initialization in the auction model/solver flow itself.
   - The explicit bulk initializer is foreverfair\foreverfair\sample_bids.py, which:
       a) creates Consent rows (quantity=1.0) per trader/period,
       b) creates one BidSet per (trader, auction, period),
       c) inserts five Bid rows per BidSet (fixed price/quantity ladder).
   - The Django admin can also create BidSet/Bid rows manually.

2. When bids are adjusted with alpha, where are adjusted bids stored?
   - Bids are not alpha-adjusted and re-stored as adjusted Bid rows.
   - Alpha is computed onto ControlPointMaxDrawdown.alpha (hydrology/models.py, update_alpha pre_save).
   - The alpha-scaled quantity is stored in ConstraintQuota.value, with alpha denormalized in
     ConstraintQuota.alpha (auctions/models.py, calculate_constraint_quotas).
   - Therefore, alpha-adjusted values are stored in ConstraintQuota, not in Bid/BidSet.

3. From which table does optimization read bids?
   - The solver reads bids via Bid.objects.filter(set__auction=auction)
     (foreverfair\foreverfair\solve_water_LP.py).
   - BidSet is used for grouping by trader/period; bid quantity/price inputs are from Bid rows.

4. After solution, which trader-related tables does the code write to?
   - In the reviewed legacy Django solver path: none.
   - foreverfair\foreverfair\solve_water_LP.py constructs LP, solves, writes LP file, and deletes LP,
     but does not persist BidSetResult, CashTransaction, Consent, or other trader-result rows.
   - BidSetResult exists as a model (and get_quota reads it), but the solver path shown does not create it.
