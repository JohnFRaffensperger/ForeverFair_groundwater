- bid entry and deletion
- manager setup/run/reset pages

Major missing features
0. other
- Make SVG file of Tianqiao.

1. Auction calendar and period model
- Add a real auction calendar module.
- Store real auction open time, close time, and delivery periods as dates/timestamps, not just display labels.
- Support the legacy period model explicitly: daysInPeriod, numberOfPeriods, and period indices for repeated weekly or seasonal auctions.
- Support manager-controlled system time for demonstration and replay, instead of relying only on wall-clock time.

2. Consent / rights registry
- Allow registration of a trader with no associated well, so they can submit purchase bids on behalf of an control point; model this explicitly rather than requiring a dummy well row.

3. Quota / allocation ledger
- Distinguish quotaAuctionStart, quotaAdjusted, and quotaAuctionEnd, i.e. initial allocation, post-adjustment allocation, and final usable quota.

4. Quota-adjustment workflow
- Recreate the AdjustQuota.py capability.
- Support pre-solve quota scaling or adjustment on a well-by-well basis when hydrologic constraints bind.
- Make the policy visible in manager tools and API output.

5. Richer bid structure
- Allow the programmer or auction manager to specify the number of bid steps.
- Add support for default bids via an is_bid_default-style flag.
- Update UI, models, repository, and solver accordingly.
- Create environmental trader page to buy water at each assessment point. Extra names: Shi Lian'ou, Gan Qincai, Zang Húluobo, Jing Ludou, Kuaile Lajiao, Xingyun Huayecai, Hong Dama

6. Bid workflow improvements
- Add bid carry-forward so a new auction can start from each well's previous bids unless the trader edits them.
- On bid resubmission, replace the well's previous bid schedule cleanly rather than accumulating stale rows.
- Add manager bulk-bid entry so the manager can set default or proportional bids for many wells at once.
- Add a quick way to initialize bids as fractions of well quota with corresponding prices, as in the legacy manager UI.

7. Legacy auction status fields and diagnostics
- Add explicit solve status, solve start time, solve completion time, and solver message fields to auctions or auction_runs.
- Capture solver stdout/stderr or equivalent diagnostic output, not just a final status string.
- Add timeout/error reporting for long or failed solves.

8. Auction revenue and participation tracking
- Track how many participants have submitted bids for a given auction.

12. Alpha / constraint-scaling parameter
- The Django prototype auto-computes an alpha scaling factor per constraint from the response matrix and bound, pre-solve.
- This normalises constraints so the LP solver works with well-conditioned coefficients.
- Add equivalent pre-solve scaling to RunAuctionModule and make the scaling parameters visible in solver diagnostics.
- Store computed alpha values alongside constraint results for audit.

12a. Configuration table / run control
- Legacy code uses configs to define the current auction and other run controls.
- Add explicit system configuration storage rather than relying on implicit defaults.
- Make current auction, active case, current simulated date, policy settings, and solver options configurable from the database/UI.

13. Bootstrapping utilities for new cases
- Recreate the practical role of dbtest.py and ForeverFairUtilities.py.

17. Solver diagnostics and reproducibility
- Keep LP files, solver settings, and run summaries together.
- Surface infeasible/unbounded diagnostics more clearly in manager tools.

18. Demand-curve and market visualization
- Add trader-side visualization of the entered bid curve before submission. Create an SVG demand-curve display tied to the stepped bid points.
- Add SVG map of the catchment showing prices at each well and control point. Check lat/long of Tianqiao wells and control points.
- Put a map on every page "Your wells here".

22. Input/output model separation for bids
- The Django prototype cleanly separates Bid (what the trader submitted) from BidSetResult (what the solver accepted and priced).
- Currently ForeverFair2026 conflates these; the bid table is updated with accepted quantities after the solve.
- Enforce strict separation: bids are immutable once submitted; results are written to a distinct results table.
- This simplifies re-running the solver without touching submitted data.

23. Data validation framework
- The Django prototype uses approximately 15 pre-save signal validators covering: auction date ordering, bid quantity against consent, closed-auction protection, and period range checks.
- Currently BiddingController does some validation but it is sparse.
- Add a systematic validation layer in BiddingController and AuctionController that raises clear errors for each violation category.
- Include: period outside auction range, invalid price or quantity, duplicate bid for same well/period.
