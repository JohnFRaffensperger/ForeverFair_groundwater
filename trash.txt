Plan to add an environmental trader who buys aquifer head at control point events

1. Database changes first

The current schema is built around physical wells. That is visible in `wells`, `well_license`, `well_quota`, `well_bids`, `response_matrix`, and in the data-access methods that assume every bid is keyed by `well_id`. An environmental trader should not be modeled as a fake well, because fake wells would immediately collide with quota scaling, response factors, location fields, and settlement logic that assume physical pumping.

Preferred database changes:

- Add `trader_type TEXT NOT NULL DEFAULT 'well'` to `traders`.
	Use values `well` and `environmental`.
	This becomes the root switch for login, page routing, quota logic, and validation.

- Keep `wells` unchanged for physical traders.
	Environmental traders should have no rows in `wells`.
	That cleanly enforces “no latitude/longitude, no gw_model_layer/row/column, no initial license, no quota scaling”.

- Add a new table for environmental bids, parallel to `well_bids`, but keyed to control point events instead of wells.

	Suggested table:

	`environmental_bids (
			env_bid_id INTEGER PRIMARY KEY AUTOINCREMENT,
			trader_id INTEGER NOT NULL,
			auction_id INTEGER NOT NULL,
			cpe_id INTEGER NOT NULL,
			bid_date TEXT NOT NULL,
			is_bid_default INTEGER DEFAULT 0,
			qty1 REAL, price1 REAL,
			qty2 REAL, price2 REAL,
			qty3 REAL, price3 REAL,
			qty4 REAL, price4 REAL,
			qty5 REAL, price5 REAL,
			deleted INTEGER NOT NULL DEFAULT 0,
			FOREIGN KEY (trader_id) REFERENCES traders(trader_id),
			FOREIGN KEY (auction_id) REFERENCES auctions(auction_id),
			FOREIGN KEY (cpe_id) REFERENCES control_point_events(cpe_id)
	)`

	The quantity here should be in head units for that control point event, not water units. 
	That matches the existing control-point constraint dual price much better than inventing a fake well quota.

- Add a new table for cleared environmental positions, parallel to `well_quota`, but keyed to `cpe_id`.

	Suggested table:

	`environmental_position (
			env_position_id INTEGER PRIMARY KEY AUTOINCREMENT,
			auction_id INTEGER NOT NULL,
			trader_id INTEGER NOT NULL,
			cpe_id INTEGER NOT NULL,
			head_start REAL,
			head_end REAL,
			price REAL,
			FOREIGN KEY (auction_id) REFERENCES auctions(auction_id),
			FOREIGN KEY (trader_id) REFERENCES traders(trader_id),
			FOREIGN KEY (cpe_id) REFERENCES control_point_events(cpe_id)
	)`

	For the first version, `head_start` should normally be `0.0`. Environmental traders have no initial license, so there is no scaling path and no inherited head allocation to preserve.

- Add indexes matching the access path.
	At minimum:
	`INDEX environmental_bids(auction_id, trader_id, cpe_id, deleted)`
	`INDEX environmental_position(auction_id, trader_id, cpe_id)`

2. Database population and admin workflow

- Extend trader creation/import so a trader can be marked `trader_type='environmental'`.
- Do not require any well assignment for environmental traders.
- Do not create `well_license` rows for environmental traders.
- Do not create `well_quota` rows for environmental traders.
- Do not try to georeference them; their market object is the control point event itself.

Because this project is prototype-first and recreates databases, implement this directly in `SetupForeverFairDB.py` and the relevant import/setup helpers. Do not add migration code.

3. Data-layer refactor in `ForeverFairData.py`

The current data layer is explicitly well-centric. The following methods show the main assumption boundary:

- `get_trader_wells`
- `add_bid`
- `get_bids`
- `get_bid_history`
- `get_default_bids`
- `copy_active_bids_for_well`
- `has_active_bids_for_well`
- `has_real_bids_for_well`
- all quota readers based on `well_quota`

Add a parallel environmental path rather than forcing these methods to handle both shapes in one signature.

Suggested additions:

- `get_trader_type(trader_id)`
- `get_environmental_bid_rows(auction_id)`
	Returns the active control point events for an auction, with control point name, effect date, allowable change, planned/committed heads, last auction clearing price, and the trader’s latest bid if any.
- `add_environmental_bid(auction_id, trader_id, cpe_id, bid_steps, is_default=False)`
- `get_environmental_bid_history(auction_id, trader_id)`
- `has_active_environmental_bids(auction_id, trader_id, cpe_id)`
- `copy_active_environmental_bids(auction_id, source_auction_id, trader_id)`
- `get_environmental_positions(auction_id, trader_id)`

Keep the well-trader methods intact for physical traders. The route/controller layer can branch on `trader_type`.

4. Auction model changes in `AuctionController.py`

This is the core market-design change.

Current model:

- well bid variables increase pumping at `(well_id, pumping_period)`
- control point event constraints limit aggregate drawdown at `(control_point_id, effect_period)`
- dual prices on those constraints become the shadow value of aquifer head

Environmental trader interpretation:

- an environmental bid is a buy-only demand for additional protected head at a specific control point event
- therefore its variable should be attached directly to a specific `cpe_id`
- it should never go negative, so environmental traders can buy but never sell

Recommended LP change:

- Add environmental bid decision variables keyed by `(trader_id, cpe_id, step_num)`.
- Sum them into an environmental purchase quantity `env_qty[cpe_id]`.
- Modify each control point event constraint from:

	`drawdown <= available_head_change`

	to:

	`drawdown + env_qty[cpe_id] <= available_head_change`

	where `env_qty[cpe_id] free`. Since the bid step variables  are >= 0, the env_qty does not need a zero lower bound.

This means the environmental trader buys tighter protection at that exact event. The same constraint dual price then clears both water demand and environmental demand in one model.

- Add environmental bid value to the objective, just like trader bid value is added now.
- Reuse the existing max-step bid structure.
- Do not include environmental traders in `ffdata.get_wells()` or the response-matrix loops.

5. Settlement and post-solve writes

Current settlement assumes everything resolves through `well_quota` and, for scaled-rights policies, through `quota_scaled_start`.

Environmental traders must bypass that completely.

Implementation plan:

- After solve, write environmental clearings into `environmental_position`.
	For each `(trader_id, cpe_id)` write:
	- `traded_head_start = 0.0`
	- `traded_head_end = cleared environmental quantity`
	- `price = control point event dual price`

- Settlement for environmental traders should be:

	`payment to the auction manager = traded_head_end * price` so they always pay or pay zero, never receive.
	Example: committed aquifer head at auction start is 800. The environmental trader buys 0.10 meters at a dual price of $5000/meter. 
	The payment to the auction manager is therefore 0.10*%5000 = $500.

- Keep existing well-trader settlement unchanged.
- Extend auction revenue calculation to include environmental purchases.
- Exclude environmental traders from:
	- `calculate_and_set_constraint_alphas`
	- `set_quota_scaled_start`
	- any `well_quota` settlement logic

6. Validation rules

- Only traders with `trader_type='environmental'` may submit environmental bids.
- Environmental bids must target valid `cpe_id` rows in the current auction.
- Environmental bid quantities and prices must be positive.
- No negative environmental quantity anywhere in the pipeline.
- No sell path in UI, data layer, or optimization model.
- No requirement for wells, coordinates, grid indices, or licenses.

7. Standing/default bids

The current system carries forward well standing bids auction-to-auction. Environmental traders will likely want the same behavior.

Plan:

- Copy active environmental bids from the previous auction to the new auction for matching control point events.
- Match by `(control_point_id, effect_date)` or by the new auction’s `cpe_id` after resolving that event identity.
- Do not try to match by raw `cpe_id` across auctions if `cpe_id` is regenerated every auction.

This identity rule should be decided early, because it affects history, defaults, and the bidding page labels.

8. Routing and page selection in `ForeverFairPages.py`

Current `/trader` flow assumes:

- the trader has wells
- one well is selected in a cookie
- the bid grid is built from `period_rows`

That flow should branch immediately on `trader_type`.

Plan:

- `well` trader: keep existing page behavior.
- `environmental` trader: build a separate context based on control point events instead of wells.

Suggested controller additions:

- `_build_environmental_trader_context(request)`
- route branch inside `/trader` to render either the current well-trader template or a new environmental trader template

9. History/reporting changes

Environmental bid history should parallel the current last-auction table, but use control point event fields.

Needed fields:

- control point name
- control point id
- control point event id
- effect date
- bid steps
- purchased head quantity
- clearing price
- receipt (always negative or zero)

This should not depend on `well_quota`.

10. Tests

Add focused tests for:

- creating an environmental trader with no wells
- posting environmental bids to multiple control point events in one auction
- rejecting negative quantity or any sell-like path
- clearing an auction with both well bids and environmental bids together
- verifying environmental purchase tightens the relevant control point constraint
- verifying environmental trader is excluded from quota scaling
- verifying environmental receipt is never positive
- verifying standing environmental bids carry forward correctly

11. Description of the environmental trader bidding page

The environmental trader should get a different bidding page from the physical well trader.

Top of page:

- show trader name and trader id
- identify the trader as an environmental trader
- do not show well name, well id, coordinates, or well-switch buttons

Main bidding table:

- one row per active control point event in the current auction
- because the environmental trader may want to buy from multiple events at once, all active events should appear on one page at the same time
- each row should show:
	- control point name
	- control point id
	- control point event id
	- effect date/time
	- committed head at auction start/end if useful
	- planned head at auction start/end if useful
	- allowable head change remaining
	- last auction clearing price for that event if available
	- bid step inputs `qty1/price1 ... qtyN/priceN`

Quantity units on this page should be explicit, for example “metres of protected head” or whatever final unit name is chosen for environmental purchases. Do not reuse “cubic meters quota” labels here.

History table:

- same overall style as the current trader history table
- one row per control point event bid
- show cleared purchased head, clearing price, and receipt
- receipt should always be zero or negative

Usability goal:

- environmental traders should be able to post one multi-event submission page per auction without any reference to wells or scaled quota
- the page should make it obvious that these bids buy tighter environmental protection at selected control point events, not water extraction rights
