Programmer's page

The software architecture for web routes and pages is the FastAPI app in src/web/app.py. An SQLite repository provides data persistence in src/services/repository.py. The sqlite3 transactions commit only after each stage succeeds. Repeated imports of the same case don't hurt. The linear programming optimization solver is PuLP model in src/RunAuctionModule.py. Auction orchestration is done in src/AuctionController.py and src/BiddingController.py.

Installing the necessary Python libraries

1. From the workspace root (folder ForeverFair2026), install all dependencies. This installs FastAPI, Uvicorn, Jinja2, PuLP, Pydantic, Python-multipart, pytest, and httpx from the project's pyproject.toml:

pip install -e ".[dev]"

2. To start the development server after installation, run:

python -m uvicorn src.web.app:app --reload

3. Open your browser to http://127.0.0.1:8000/.

4. Your hydrologist should run the hydrology model through GWM2K or similar to export a linear program, with decvar, hedcon, and mps files. This code here reads those files to get the response matrix, the number of wells, the number of control points, and the number of time periods. In principle, then, this code will work with any groundwater model that works with GWM2K. Buttons below allow you to import these files, and import_gwm2k.py runs the steps in sequence.

Setting up the database: 7 files

Create an empty database above if you haven't done so already. Then let's populate it with the catchment data.

1. Import .decvar file

Forever Fair uses this data for the list of wells. A GWM2K .decvar file defines decision variables as "wellNNNN NC LAYER ROW COL FTYPE FSTAT stress_period". The layer, row, and col fields are the MODFLOW grid coordinates. Module import_decvar.py stores this data in table wells with one well row per unique well number. (Confusingly, GWM2K writes wellNNNN as a single running index over the Cartesian product of wells and pump periods. So one index NNNN encodes well number and time period. The import_decvar.py importer unpacks that encoding and inserts only one row per unique well number with name generated as Well {well_num}.)

2. Import .hedcon file

Forever Fair uses this information for the list of control points and head constraints by time periods. A GWM2K .hedcon file lists head constraints (bonNNNN LAYER ROW COL SENSE RHS_head stress_period). The RHS value is important: it is the groundwater-head constraint target for that control point and stress period, i.e., the water table must stay above RHS m. Module import_hedcon.py creates one control-point row per unique control-point number in table control_points. The module also stores per-period bounds from RHS_head in table default_control_point_bounds. These defaults are used by the optimizer whenever no auction-specific bounds have been applied via the Hydrologist maintenance page. (Like the wellNNNN convention in the GWM2K .decvar file, GWM2k formats control-point tokens in HEDCON as bonNNNN.)

3. Import .mps file

Forever Fair gets the groundwater response matrix from this file. A GWM2K .mps file contains the response matrix (COLUMNS section), head-constraint right-hand sides (RHS section), and well capacities (BOUNDS section). The COLUMNS section is the important part, because it contains the response matrix. RHS is a repeat from the hedcon file. Forever Fair ignores well capacities, because users are on their own to know their well capacities; the auction manager is not responsible if they try to buy more than their well capacity. This is a valuable feature, because the auction design allows users to increase their well capacity without notifying anyone. Module import_mps.py writes to tables response_matrix and default_control_point_bounds. The BOUNDS section is read to ensure well rows exist (fallback if DECVAR was not imported first), but the capacity values are not stored. Import populates the response_matrix table (auction-scoped) and default_control_point_bounds (RHS bounds, no auction, used as optimizer fallback). control_point_bounds is left empty; apply defaults for a specific auction from the Hydrologist maintenance page. Requires an existing manager-created auction for response factors. Default dimensions are from the Tianqiao example. Caution, import may be slow because these can be big files. Control-point token format in MPS rows: numeric row name.

control_point = 1 + floor((row_index - 1) / number_control_periods)
effect_period = 1 + (row_index - 1) mod number_control_periods

4. Import trader names

Upload a tab-delimited file with columns full_name, trader_first_name, and trader_last_name. A template file is at data/Tianqiao/Trader_names.csv.

The import derives trader_id, name, and trader_loginid from the last name. If the same last name appears more than once in the file, a numeric suffix is appended to each duplicate (e.g. Li, Li1, Li2).

5. Import trader-well assignments

Upload a tab-delimited file with columns name and well_id. A template file is at data/Tianqiao/Trader_wells.csv.

Requirements:

  • name must exactly match a value in the traders.name column (case-sensitive).
  • well_id must exactly match a value in the wells.well_id column.
  • A trader may have more than one well; each well can be assigned to only one trader.

The import updates wells.trader_id for each matched row. Rows that fail either check are skipped and listed in the notice.

6. Import well latitude and longitude

Upload a tab-delimited file with columns well_id, latitude, and longitude. Updates the wells table with spatial coordinates.

7. Import control point latitude and longitude

Upload a tab-delimited file with columns control_point_id, latitude, and longitude. Updates the control_points table with spatial coordinates.

Deferred feature: auction cash ledger (E.1)

This project currently does not implement the legacy cash-ledger behavior. Auction results are stored in traderquota, but no explicit transaction journal is written for each trader. A robust implementation would add a dedicated table such as cash_transactions with fields for trader, auction, period, transaction type, quantity, unit price, signed cash value, timestamp, and source run id. During save_run_results(), insert one ledger row per trader-period result so balances are auditable and reproducible. Add repository helpers to return running balances and transaction history, and expose these on Trader and Researcher pages. Keep writes idempotent per run id.
