Forever Fair Database Documentation

This page documents the SQLite schema for Forever Fair. SetupForeverFairDB.create_empty_db creates the schema from SCHEMA_DDL in src/SetupForeverFairDB.py. ForeverFairData methods in src/ForeverFairData.py and import helpers in src/SetupForeverFairDB.py write and read most table values.

Initialization convention: Setup import functions write auction_id = 0 rows into both well_quota (initial quota via quota_auction_start) and control_point_events baseline data paths. During solve, AuctionController.runCurrentAuction builds LP right-hand sides from minimum_head − committed_head_auction_start.

Table: Catchment_info

meta_key (TEXT, PRIMARY KEY): Name of a global catchment setting. Used for keys such as inferred GWM dimensions, synthetic time, period length, and bidding-period count.

meta_value (TEXT, NOT NULL): Value for the setting key, stored as text and interpreted by caller logic.

Common keys: synthetic_current_date, num_bidding_periods, period_length_hours, mps_loaded_date, mps_notes, gwm_num_wells, gwm_num_pump_periods, gwm_num_control_points, gwm_num_control_periods.

Table: traders

trader_id (INTEGER, PRIMARY KEY AUTOINCREMENT): Internal numeric trader identifier used throughout joins and foreign keys.

name_tag (TEXT, NOT NULL): Trader display/name key used by UI and several import joins (for example trader-well assignment import). One trader can own more than one well.

trader_loginid (TEXT): Login identifier value imported with trader names. SetupForeverFairDB.import_trader_names currently derives it from surname.

trader_password (TEXT): Reserved legacy column for password storage; not used by current auth flow.

trader_first_name (TEXT): Trader first name imported from trader names file.

trader_last_name (TEXT): Trader last name imported from trader names file.

trader_address (TEXT): Reserved contact/location field.

trader_city (TEXT): Reserved contact/location field.

trader_phone (TEXT): Reserved contact field.

trader_email (TEXT): Reserved contact field.

Table: wells

well_id (INTEGER, PRIMARY KEY AUTOINCREMENT): Internal well identifier used by bids, response matrix rows, and quota/result tables.

name (TEXT, NOT NULL): Well label (for example gwm-well-N). SetupForeverFairDB.import_decvar writes these names for display and matching.

trader_id (INTEGER, FOREIGN KEY to traders.trader_id): Assigned owner/trader for the well. SetupForeverFairDB.import_trader_wells writes this field. One trader can own more than one well.

gw_model_layer (INTEGER): Groundwater model layer index. SetupForeverFairDB.import_decvar writes this field.

gw_model_row (INTEGER): Groundwater model row index. SetupForeverFairDB.import_decvar writes this field.

gw_model_column (INTEGER): Groundwater model column index. SetupForeverFairDB.import_decvar writes this field.

latitude (REAL): Well latitude. SetupForeverFairDB.import_well_lat_lon writes this field.

longitude (REAL): Well longitude. SetupForeverFairDB.import_well_lat_lon writes this field.

Table: control_points

control_point_id (TEXT, PRIMARY KEY): Control point identifier (for example gwm-cp-N), used across constraints and events.

name (TEXT, NOT NULL): Display name for control point.

gw_model_row (INTEGER): Groundwater model row index for control point.

gw_model_column (INTEGER): Groundwater model column index for control point.

latitude (REAL): Control point latitude.

longitude (REAL): Control point longitude.

Table: auctions

auction_id (INTEGER, PRIMARY KEY AUTOINCREMENT): Auction identifier used for all auction-scoped data.

status (TEXT, NOT NULL): Auction lifecycle state (for example OPEN/CLOSED).

created_date (TEXT, NOT NULL): Timestamp when auction row was created.

closed_date (TEXT): Scheduled close datetime (also used in page logic to infer closure).

firstWaterTakeDate (TEXT): First settlement/take period datetime anchor.

lastWaterTakeDate (TEXT): Last settlement/take period datetime anchor.

period_length_hours (INTEGER): Period size in hours for this auction context.

auction_type (TEXT): Auction category (for example tentative vs final).

solve_status (TEXT): LP solver status from latest run.

objective_value (REAL): Objective value from latest solved run.

Table: response_matrix

well_id (INTEGER, NOT NULL, FOREIGN KEY to wells.well_id): Source well for response coefficient.

control_point_id (TEXT, NOT NULL, FOREIGN KEY to control_points.control_point_id): Affected control point.

pumping_period (INTEGER, NOT NULL): Pumping period index in response matrix dimension.

effect_period (INTEGER, NOT NULL): Effect period index in response matrix dimension.

response (REAL, NOT NULL): Response factor coefficient linking pumping to control-point effect. SetupForeverFairDB.import_mps writes these coefficients, and AuctionController.runCurrentAuction reads them through ForeverFairData.get_response_factors_for_auction. The hydrologist may choose to omit rows with very small coefficients to keep the database compact; however, the rounding threshold must be chosen very carefully, because omitting small-but-numerous coefficients can systematically undercount the total hydrological effect at a control point and cause the market to accept more pumping than the aquifer can safely sustain. They hydrologist should also inspect response matrix coefficients (also called factors) that are positive, which implies injection rather than withdrawal. The Tianqiao data (tiansqiao.decvar) has only withdrawals, but the response matrix does have some positive values. Inside SetupForeverFairDB.import_mps, function SetupForeverFairDB.censor_the_response_matrix runs before each response row is written. The Tianqiao data has dodgy response matrix values for lags over 22 periods, so I added some code to fix it on the fly.

Primary key: (well_id, control_point_id, pumping_period, effect_period).

Table: response_matrix_info

Removed: The current setup code does not create this table. SetupForeverFairDB.save_catchment_info writes those settings into Catchment_info key/value rows.

Table: well_license

license_id (INTEGER, PRIMARY KEY AUTOINCREMENT): License row identifier.

trader_id (INTEGER): Trader for this license row.

well_id (INTEGER): Well associated with this license row.

license_quantity (REAL): Licensed quantity value for the period.

license_date (TEXT): Optional source/license date-time for this row.

bid_period (INTEGER): Integer bid period index (for example 1..26).

Table: well_quota

quota_id (INTEGER, PRIMARY KEY AUTOINCREMENT): Trader quota event row identifier.

trader_id (INTEGER): Trader associated with this quota result.

auction_id (INTEGER): Auction that produced this quota row.

well_id (INTEGER): Well context for this quota row.

quota_auction_start (REAL): Initial/starting quantity prior to market adjustment.

quota_scaled_start (REAL): Quantity adjustment from clearing outcome.

quota_auction_end (REAL): Final quantity after adjustment.

price (REAL): Price associated with the row's auction-period settlement.

take_date (TEXT): Period/date key for the quota row.

Table: control_point_events

cpe_id (INTEGER, PRIMARY KEY AUTOINCREMENT): Control-point event row identifier.

control_point_id (TEXT): Control point associated with event/result row.

auction_id (INTEGER, FOREIGN KEY to auctions.auction_id): Auction scope.

effect_date (TEXT): Effect period/date key for the row.

committed_head_auction_start (REAL): Start head for the committed track in this auction row. On auction setup, ForeverFairData.set_control_point_events_for_auction copies the latest prior committed_head_auction_end for the same (control_point_id, effect_date). If no prior auction row exists, that function falls back to aquifer_head_limits.actual_start_head.

committed_head_auction_end (REAL): End head for the committed track after solve. ForeverFairData.set_auction_solution_results_bulk writes committed_head_auction_start + committed_head_change into this field.

committed_allowable_head_change (REAL): Remaining committed head allowance after solve. ForeverFairData.set_auction_solution_results_bulk writes aquifer_head_limits.minimum_head - committed_head_auction_end into this field.

planned_head_auction_start (REAL): Start head for the planning track in this auction row. On auction setup, ForeverFairData.set_control_point_events_for_auction copies the latest prior planned_head_auction_end for the same (control_point_id, effect_date). If no prior auction row exists, that function falls back to aquifer_head_limits.actual_start_head.

planned_head_auction_end (REAL): End head for the planning track after solve. ForeverFairData.set_auction_solution_results_bulk writes aquifer_head_limits.minimum_head + slack into this field.

slack (REAL): Solver output slack for the control-point constraint period. AuctionController.runCurrentAuction computes it from the LP constraint, and ForeverFairData.set_auction_solution_results_bulk writes it.

dual_price (REAL): Solver output dual price for the control-point constraint period. AuctionController.runCurrentAuction computes it from the LP constraint, and ForeverFairData.set_auction_solution_results_bulk writes it.

alpha (REAL): Constraint scaling value for this event row. ForeverFairData.calculate_and_set_constraint_alphas computes and writes alpha, and ForeverFairData.set_constraint_alphas can also write alpha values.

Committed versus planned

Since the auction calendar runs the full season, traders and the auction manager must commit only in the auction period, e.g., the current week. At the end of an auction, everyone expects wells to actually take the allocated quota for the immediate next week. Following weeks are only plans and subject to change. Committed aquifer head depends on quota allocated in the most-recently closed auction for that auction period. That committed quota will affect future periods.

Based on ForeverFairData.get_control_point_events, function AuctionController.runCurrentAuction forms the right-hand-side constraint coefficients for allowable head change. After solving the linear program, the function computes committed head change from pumping period 1 only (the committed period); committed head change is the modeled head change at one control point and one effect_date caused only by pumping in the auction period pumping (pumping_period = 1). To do this, the function sums response_matrix(well, pumping_period=1, effect_period, control_point) × cleared_quantity(well, pumping_period=1) across wells.

Then ForeverFairData.set_auction_solution_results_bulk writes committed_head_auction_end = committed_head_auction_start + committed_head_change. Function ForeverFairData.set_auction_solution_results_bulk carries forward planned aquifer heads between auctions, and it computes planned end head from full-LP constraint slack for each effect period.

Carry-forward rules for auction_id at (control_point_id, effect_date):

  • planned_head_auction_start(auction_id) = previous planned_head_auction_end, else aquifer_head_limits.actual_start_head.
  • committed_head_auction_start(auction_id) = previous committed_head_auction_end, else aquifer_head_limits.actual_start_head.

After the user of Programmer.html uploads a new aquifer head CSV, function ForeverFairData.update_aquifer_head_limits writes the new aquifer_head_limits.actual_start_head values into the database. In one transaction, the function synchronizes control_point_events rows for the first open auction:

  • set committed_head_auction_start = aquifer_head_limits.actual_start_head,
  • set committed_allowable_head_change = aquifer_head_limits.minimum_head - aquifer_head_limits.actual_start_head,
  • set planned_head_auction_start = aquifer_head_limits.actual_start_head,
  • and clear stale solve outputs: set committed_head_auction_end = NULL, set planned_head_auction_end = NULL; clear slack, dual_price, and alpha.

This synchronization aligns committed and planned heads with the uploaded forecast before the next call to AuctionController.runCurrentAuction.

Upload File Format: new aquifer head limits

Route and parser: Programmer.html posts the file to /setup/import-aquifer-head-limits, and ForeverFairData.update_aquifer_head_limits parses the text with Python csv.DictReader.

Required CSV columns:

  • control_point_id: integer control-point identifier.
  • effect_date: ISO-like datetime text label matching the database effect_date values (for example 2030-03-04T00:00).
  • actual_start_head: numeric head value (float).

Validation rules enforced by update_aquifer_head_limits:

  • The file must not be empty.
  • The header must include control_point_id, effect_date, and actual_start_head.
  • The earliest effect_date in the file must equal first_pumping_date for the first open auction.
  • The set of (control_point_id, effect_date) keys in the file must exactly match control_point_events rows for the first open auction: no missing keys and no unexpected keys.
  • For each row, the code computes allowable_head_change = minimum_head - actual_start_head and updates aquifer_head_limits.

Practical guidance: provide one row per (control_point_id, effect_date) in the open-auction horizon, using the same effect_date labels already present in the database.

How to use the API link

The navigation link API opens /api/system-state. That endpoint returns JSON describing the current catchment and auction state. It is intended for programmers, scripts, and integration code, not for a formatted human report.

The main fields in the JSON response are: catchment_name, auction, rights_conversion, latest_run, well_price_rows, control_point_rows. Here are five use cases for the programmer:

  1. Automated health check: poll /api/system-state every minute and alert if latest_run.solve_status indicates a failed run or if the response contains an error field.
  2. Dashboard integration: feed well_price_rows and control_point_rows into a custom charting page so operations staff can monitor prices and binding constraints without opening the full web UI.
  3. Auction-run regression tests: after running a test auction, compare key JSON fields (objective_value, auction_revenue, selected prices) against expected values in CI.
  4. Data export for research: save periodic snapshots of /api/system-state to files, then analyse time trends in prices, dual values, and control-point usage in Python or R.
  5. External workflow trigger: call /api/system-state from an orchestration script and trigger follow-up jobs (for example notification emails or report generation) when a new auction closes.

Security hardening for production deployment

This research code is intentionally simple and is not ready for commercial deployment. A production water-trading website should follow current security practice (for example OWASP ASVS, OWASP Top 10, and your local privacy and critical-infrastructure obligations).

Minimum authentication and authorization changes

  • Require username + password login for every role (trader, auction manager, programmer, hydrologist, researcher).
  • Store only password hashes (never plaintext passwords). Use Argon2id or bcrypt with strong parameters.
  • Replace the current cookie-only trader identity approach with signed, expiring sessions or short-lived tokens.
  • Implement role-based access control for every route and API endpoint.
  • Add multi-factor authentication for administrator roles.
  • Add account lockout, throttling, and audit events for failed login attempts.

Transport, browser, and request protection

  • Serve only over HTTPS behind a hardened reverse proxy (Nginx, Caddy, or Traefik).
  • Set secure headers: HSTS, CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, and secure cookie flags.
  • Enable CSRF protection for state-changing form posts.
  • Restrict CORS to trusted origins only.
  • Add per-IP and per-account rate limits on login, bidding, and upload endpoints.

Data and operations security

  • Move secrets from local files into a managed secret store in production.
  • Add structured security logging (auth events, privilege changes, uploads, auction runs) and central monitoring.
  • Add automated dependency and container scanning, plus regular patching.
  • Encrypt backups, test restore procedures, and protect database files with strict filesystem permissions.
  • Add tamper-evident audit trails for bids, quota changes, and administrative actions.

Open-source security packages

Example Python packages you can use:

  • pwdlib or argon2-cffi: password hashing (Argon2id).
  • Authlib or python-jose[cryptography]: token and OAuth/OpenID flows.
  • starlette-csrf: CSRF protection for form posts.
  • slowapi: request rate limiting for FastAPI.
  • secure: HTTP security header policy helper.
  • fastapi-users: user management scaffolding (optional, if you want a full auth framework).

Example installation commands:

pip install -e ".[dev]"
pip install pwdlib argon2-cffi authlib "python-jose[cryptography]" starlette-csrf slowapi secure fastapi-users[sqlalchemy]

Commercial deployment should also include a threat model, penetration testing, independent code review, incident response planning, and legal/compliance review before go-live.
