The Forever Fair market is centered on a groundwater model. The hydrologist has a key role! The groundwater model is the source of the response matrix, well locations, and head constraints at control points. The response matrix is a linearized representation of the hydrology; its values describe the effect of pumping from wells and head at various control points. Through the response factors, each accepted bid affects the control point constraints. Since hydrologic effects propagate over time, the market clearing optimization must support lagged responses, so pumping does not injure control points in future periods. Therefore, to set up the market, the programmer needs a groundwater model that can produce this response matrix. The hydrologist must define environmental limits as control points with head limits. This is best done with code like USGS GWM Groundwater Management Process. GWM can produce important files needed: decvar, hedcon, and mps. But the hydrologist must set this up!

To set up the market clearing database, the hydrologist should prepare these groundwater files for the programmer:

  • your_file_name.decvar listing the wells with MODFLOW layer, row, and column,
  • your_file_name.hedcon listing the control points,
  • and your_file_name.mps which has the response matrix, control point head limits by time period, and initial rights records.

This software version assumes that the physics of the aquifer do not change with the auction schedule. Therefore, this version treats the response matrix timing as relative, i.e., the effects in a relative number of periods after pumping occurs. This allows one response matrix to be used for multiple auctions. The hydrologist should confirm the sign convention for response factors and bounds. Check that period indexing is consistent across all files. Verify that each active well has response coefficients for each required control point and period. Validate that bound values and units match bid quantities. Run a small known case and compare prices and accepted quantities with independent calculations.

Period indexing convention: period 1 in the response matrix always means the first pumping period in the hydrology model, not a fixed calendar date. During auction clearing, these model periods are remapped to the auction's local timeline.

Units convention

Careful with units! Forever Fair interprets all abstraction and taking quantities in the optimization as cubic meters per period. This includes initial rights imported from the MPS BOUNDS section, quota values, bid quantities, accepted quantities, and aggregate pumping variables.

Aquifer head is measured in meters. Therefore, response-matrix coefficients must be in units of meters per (cubic meter per period). For Tianqiao, one period is 168 hours, so the Tianqiao quantity unit is cubic meters per week and Tianqiao response factors are in units of meters per cubic meter per week. You can read about the Tianqiao case in Raffensperger, John F., Jin Lin, and Chunmiao Zheng, “Planning a smart market for Tianqiao groundwater,” 2010.

This means the hydrologist should treat every Tianqiao BOUNDS quantity in the MPS file as a weekly abstraction quantity in cubic meters, not megaliters. If quantities are reported elsewhere in some other unit, they should be converted before import so the MPS, quotas, bids, and response factors all remain commensurate.

Loading initial rights for the first auction

The GWM your_file_name.mps file has a BOUNDS feature for wells. The programmers of GWM themselves probably think of these well upper bounds as pump capacities. In the auction, the trader is responsible for making sure their bid quantities don't exceed their own capacity. Capacity is the trader's problem, not the auction manager's problem. The auction manager does have to pay attention to license.

After users negotiate with the auction manager as to how to adjust their seasonal license Q_seasonal into bid period license Q_bid, the hydrologist can use the GWM BOUNDS to get the users' licensed Q_bid values (not Q_seasonal) into the Forever Fair database. When exported to the your_file_name.mps, the programmer can load them into the database via Programmmer.html. The import code will save those values to the well_license table in the database, one BOUND value for each well and each bid period.

You will have set up your MPS optimization with a pumping schedule and a constraint schedule. The pumping schedule should be shorter, preferably much shorter, than the constraint schedule. For example, you might have pumping variables for 52 weeks of the year and constraint variables for the same weeks plus another 26 weeks. That ensures constraints on the delayed effects of pumping. The auction schedule has the same idea, with some extra controls. The auction "bidding periods" are the auction pumping schedule, but you can choose to run bidding periods for shorter than the schedule in your MPS file. For example, if your MPS file has 52 weeks of pumping, you can choose to run bidding periods for only 20 weeks. The purpose of having fewer bidding periods is to make bidding easier for your traders, because they must enter bids for all bidding periods in every auction, though the web page has controls to make it a bit easier. The Tianqiao example mps file has 78 weeks of constraints, of which the first 52 are also bidding periods corresponding to a calendar year. I decided to run the auction for only 20 weeks at a time, making this auction more like one farmers would use over a hydrological season rather than an auction for year-round abstraction as for urban use.

The MPS file defines gwm_num_pump_periods, the total number of pumping periods in the groundwater model. The programmer sets num_bidding_periods through the Programmer page, which must be num_bidding_periods ≤ gwm_num_pump_periods. For example, Tianqiao.mps has gwm_num_pump_periods = 52 weeks, and the auction is configured to run num_bidding_periods = 20 weeks. This ensures the optimization can access response factors for all the bidding periods, plus the lagged constraint periods that follow.

If the auction runs over a hydrological season, the final pumping period is fixed, so the auction manager should not have to convert license to quota for a new period. If the auction runs over a rolling time horizon of less than a year, the auction manager may have to convert license to quota for each new "last pumping period" in the auction. I will assume the auction runs over a hydrological season, so the final pumping period is fixed, not rolling. The schedule of pumping gets shorter as auctions progress over time. As I said above, I decided to run the auction for 20 weeks declining rather than 20 weeks rolling.

I could write a function for Programmmer.html page so the programmer can import the users' licenses separate from GWM. The input file would lists only wells and the license values. I'll postpone this feature for now.

Managing drawdown for each auction

The head-constraint bounds come from the your_file_name.hedcon and your_file_name.mps files uploaded via the Programmer page. Each time the programmer uploads hedcon and mps files, the code saves them with a timestamp. When the Auction Manager creates a new auction, the software uses the most recently imported bounds to that auction. This allows the hydrologist to re-run the groundwater simulation with an updated inflow forecast. The programmer can then import the resulting new head constraints into the auction.

Managing groundwater with real weather requires updating the head constraints in every auction. For a real auction, the hydrologist should re-load head limits that match the forecasted limits based on forecasted inflows. To update the bounds, just upload revised .hedcon and .mps files via the Programmer page. The new bounds take effect for any auction created after that upload. Auctions that were already created keep the bounds that were current when they were scheduled.

The smart market clearing model for groundwater

The following is the mathematical formulation of the Forever Fair market-clearing model. At each auction run, the software creates this optimmization from the database and solves it. The authoritative reference for this work is Raffensperger & Milke, Smart Markets for Water Resources: A Manual for Implementation.

Indices

b: bid step, b = 1, …, 5

i: well location, i = 1, …, n

t: bid period (pumping period), t = 1, …, T

cp: control point

e: effect period (period in which drawdown occurs at a control point)

Parameters

n = number of well locations

Fcp,e,i,t = drawdown response at control point cp, effect period e, due to unit pumping at well i in bid period t. Units: meters per (cubic meter per period).

Pitb = reservation price for bid step b at well i, bid period t. Positive (buy bids only).

Qitb = quantity bound for bid step b at well i, bid period t. Positive; each step is a quantity of water offered for purchase. Units: cubic meters per period.

UHcp,e = upper bound on drawdown at control point cp, effect period e. Right-hand side of the control-point constraint. Stored in control_point_events.head_constraint_upper_bound.

T = number of bid periods, e.g, 4 to 26 weeks.

Variables

biditb = quantity of bid step b accepted at well i, bid period t. Bounded [0, Qitb].

pit = market clearing price at well i, bid period t. Dual of quantity-equality constraint 3. Stored in well_quota.price.

qit = aggregate pumping at well i, bid period t. Free auxiliary variable; equals the sum of accepted bids by constraint 3.

Model

1. Objective. This is a gross-pool model with buy bids only; each accepted bid quantity yields surplus equal to Pitb per unit. Maximise consumer surplus (gross-pool; buy bids only): maximize ∑i,t,b Pitb·biditb.

2. Bid bounds. Each accepted bid quantity is nonnegative and bounded above by the step quantity Qitb. For all b, i, t: 0 ≤ biditb ≤ Qitb. Dual variables αitb ≥ 0.

3. Pumping equals the sum of bids. The dual price pit is the market clearing price at well i, period t. The code extracts this value from the solver via PuLP’s constraint.pi attribute and stores it as the well-period price. For all i, t: qit = ∑b=1..5 biditb. Dual variables pit (free).

4. Control-point drawdown constraint. For each control point cp and effect period e, the response-weighted sum of pumping must not exceed the permitted drawdown bound. λcp,e is the dual price on the drawdown limit (stored in control_point_events.dual_price). For each control point cp and effect period e: ∑i,t Fcp,e,i,t qit ≤ UHcp,e. Dual variables λcp,e ≥ 0.

5. Variable bounds. 0 ≤ biditb ≤ Qitb (constraint 2). qit is free (unconstrained in sign).

Adding minimum drawdown constraints

The current version enforces only upper-bound drawdown constraints only, corresponding to constraint 4 above. Each control point has a single bound per period: sit ≤ UHit. The database stores these bounds in control_point_events.head_constraint_upper_bound. This field is the LP right-hand side for each constraint row. After the auction runs, the code returns the dual price dual_price and slack slack for each row. This is appropriate when the environmental concern is that cumulative drawdown must not exceed a maximum permitted level, for example, to protect aquifer storage or sensitive groundwater-dependent ecosystems.

The hydrologist may want to implement minimum drawdown constraints, sit ≥ LHit. A minimum drawdown constraint would be appropriate when some pumping is required, e.g., to prevent waterlogging, manage saline intrusion upward, or maintain drainage gradients. The database schema already has the necessary column control_point_events.constraint_lower_bound. To implement minimum drawdown constraints, the hydrologist would have to make the following changes:

  • Import pipeline (src/SetupForeverFairDB.py): populate constraint_lower_bound from the .hedcon or .mps source file when a lower-bound row is present.
  • Hydrologist page: expose a form input for the lower bound alongside the existing upper-bound field, or add a separate apply-lower-bounds route.
  • Solver (src/RunAuctionModule.py): when loading control point bounds, check both head_constraint_upper_bound and constraint_lower_bound. For each control point and period, add the lower-bound row as a ≥ constraint alongside the existing ≤ constraint. In the MPS/LP structure this means adding a second row or widening the range constraint.
  • Results display: CatchmentPage.html should label which bound is binding when reporting dual prices and slacks.

Adding head difference constraints

A head-difference constraint bounds the drawdown difference between two locations i and j (constraint 6 in the model above): LHDijt ≤ sit − sjt ≤ UHDijt. These constraints enforce flow directions, hydraulic gradients, or velocity limits between two points, e.g., to prevent saline water from a tidal boundary moving inland, or to maintain a minimum gradient between an irrigation area and a river. The database schema already stores two grid locations per control point (CP_layer1/row1/col1 and CP_layer2/row2/col2, with corresponding lat/lon pairs), which is the physical basis for a two-point difference constraint. The fields LHD and UHD appear in the LP formulation but have no current storage column in control_point_events. To implement head-difference constraints, the hydrologist would have to make the following changes:

  • Schema (src/SetupForeverFairDB.py): add columns head_difference_lower_bound and head_difference_upper_bound to control_point_events, or add a separate control_point_difference_event table that references two control point rows.
  • Import pipeline: parse difference constraint rows from the .mps file and populate the new columns, linking each row to its two control points via the existing CP_layer1/2 pairs.
  • Solver (src/RunAuctionModule.py): for each difference constraint row, compute the combined response coefficient (Fiku − Fjku) for each well and period, and add the corresponding LP row. The solver must distinguish these rows from single-point bounds.
  • Results display: report the dual price (dL or dU) and slack for each active difference constraint on the CatchmentPage.
