Hydrologist's page

The Forever Fair market is centered on a groundwater model. The groundwater model is the source of the response matrix, well locations, and head constraints at control points. The response matrix is a linearized representation of the hydrology; its values describe the effect of pumping from wells and head at various control points. Through the response factors, each accepted bid affects the control point constraints. Since hydrologic effects propagate over time, the market clearing optimization must support lagged responses, so pumping does not injure control points in future periods. Therefore, to set up the market, you need a groundwater model that can produce this response matrix. You must also define environmental limits as control points with head limits. GWM2K can produce the files needed: decvar, hedcon, and mps. Reference: USGS MODFLOW.

To set up the market clearing database, you should prepare these groundwater files for the Programmer:

  • your_file_name.decvar listing the wells with MODFLOW layer, row, and column,
  • your_file_name.hedcon listing the control points,
  • and your_file_name.mps which has the response matrix, control point head limits by time period, and initial rights records.

This software version assumes that the physics of the aquifer do not change with the auction schedule. Therefore, this version treats the response matrix timing as relative, i.e., the effects in a relative number of periods after pumping occurs. This allows one response matrix to be used for multiple auctions. You should confirm the sign convention for response factors and bounds. Check that period indexing is consistent across all files. Verify that each active well has response coefficients for each required control point and period. Validate that bound values and units match bid quantities. Run a small known case and compare prices and accepted quantities with independent calculations.

Managing drawdown for each auction

The head-constraint bounds come from the your_file_name.hedcon and your_file_name.mps files uploaded via the Programmer page. Each time you upload new hedcon and mps files, the code saves them with a timestamp. When the Auction Manager creates a new auction, the software uses the most recently imported bounds to that auction. This allows you to re-run your groundwater with updated inflow forecast, and then import the resulting new head constraints into the auction.

Managing groundwater with real weather requires updating the head constraints in every auction. For a real auction, you should re-load head limits that match the forecasted limits based on forecasted inflows. To update the bounds, just upload revised .hedcon and .mps files via the Programmer page. The new bounds take effect for any auction created after that upload. Auctions that were already created keep the bounds that were current when they were scheduled.

The smart market clearing model for groundwater

The following is the mathematical formulation of the Forever Fair market-clearing model. At each auction run, the software creates this optimmization from the database and solves it. The authoritative reference for this work is Raffensperger & Milke, Smart Markets for Water Resources: A Manual for Implementation.

Indices

b: bid step, b = 1, …, 5

i: well location, i = 1, …, n

t: bid period (pumping period), t = 1, …, T

cp: control point

e: effect period (period in which drawdown occurs at a control point)

Parameters

n = number of well locations

Fcp,e,i,t = drawdown response at control point cp, effect period e, due to unit pumping at well i in bid period t

Pitb = reservation price for bid step b at well i, bid period t. Positive (buy bids only).

Qitb = quantity bound for bid step b at well i, bid period t. Positive; each step is a quantity of water offered for purchase.

UHcp,e = upper bound on drawdown at control point cp, effect period e. Right-hand side of the control-point constraint. Stored in control_point_event.CPE_head_constraint_upper_bound.

T = number of bid periods, e.g, 4 to 26 weeks.

Variables

biditb = quantity of bid step b accepted at well i, bid period t. Bounded [0, Qitb].

pit = market clearing price at well i, bid period t. Dual of quantity-equality constraint 3. Stored in traderquota.price.

qit = aggregate pumping at well i, bid period t. Free auxiliary variable; equals the sum of accepted bids by constraint 3.

Model

1. Objective. This is a gross-pool model with buy bids only; each accepted bid quantity yields surplus equal to Pitb per unit. Maximise consumer surplus (gross-pool; buy bids only): max ∑i,t,b Pitb · biditb.

2. Bid bounds. All bids are buy bids. Each accepted bid quantity is nonnegative and bounded above by the step quantity Qitb. For all b, i, t: 0 ≤ biditb ≤ Qitb. Dual variables αitb ≥ 0.

3. Quantity equality. Aggregate pumping equals the sum of accepted bids. The dual price pit is the market clearing price at well i, period t. The code extracts this value from the solver via PuLP’s constraint.pi attribute and stores it as the well-period price. For all i, t: qit = ∑b=1..5 biditb. Dual variables pit (free).

4. Control-point drawdown constraint. For each control point cp and effect period e, the response-weighted sum of pumping must not exceed the permitted drawdown bound. The dual variable λcp,e is the shadow price on the drawdown limit (stored in control_point_event.CPE_dual_price); the slack is CPE_slack. ∑i,t Fcp,e,i,t qit ≤ UHcp,e. Dual variables λcp,e ≥ 0.

5. Variable bounds. 0 ≤ biditb ≤ Qitb (constraint 2). qit is free (unconstrained in sign).

Adding minimum drawdown constraints

The current version enforces only upper-bound drawdown constraints only, corresponding to constraint 4 above. Each control point has a single bound per period: sit ≤ UHit. The database stores these bounds in control_point_event.CPE_head_constraint_upper_bound. This field is the LP right-hand side for each constraint row. After the auction runs, the code returns the dual price CPE_dual_price and slack CPE_slack for each row. This is appropriate when the environmental concern is that cumulative drawdown must not exceed a maximum permitted level, for example, to protect aquifer storage or sensitive groundwater-dependent ecosystems.

You may want to implement minimum drawdown constraints, sit ≥ LHit. A minimum drawdown constraint would be appropriate when some pumping is required, e.g., to prevent waterlogging, manage saline intrusion upward, or maintain drainage gradients. The database schema already has the necessary column control_point_event.CPE_constraint_lower_bound. To implement minimum drawdown constraints, you would have to make the following changes:

  • Import pipeline (src/setup.py): populate CPE_constraint_lower_bound from the .hedcon or .mps source file when a lower-bound row is present.
  • Hydrologist page: expose a form input for the lower bound alongside the existing upper-bound field, or add a separate apply-lower-bounds route.
  • Solver (src/RunAuctionModule.py): when loading control point bounds, check both CPE_head_constraint_upper_bound and CPE_constraint_lower_bound. For each control point and period, add the lower-bound row as a ≥ constraint alongside the existing ≤ constraint. In the MPS/LP structure this means adding a second row or widening the range constraint.
  • Results display: CatchmentPage.html should label which bound is binding when reporting dual prices and slacks.

You may want to implement head difference constraints. A head-difference constraint bounds the drawdown difference between two locations i and j (constraint 6 in the model above): LHDijt ≤ sit − sjt ≤ UHDijt. These constraints enforce flow directions, hydraulic gradients, or velocity limits between two points, e.g., to prevent saline water from a tidal boundary moving inland, or to maintain a minimum gradient between an irrigation area and a river. The database schema already stores two grid locations per control point (CP_layer1/row1/col1 and CP_layer2/row2/col2, with corresponding lat/lon pairs), which is the physical basis for a two-point difference constraint. The fields LHD and UHD appear in the LP formulation but have no current storage column in control_point_event. To implement head-difference constraints, you would have to make the following changes:

  • Schema (src/setup.py): add columns CPE_head_difference_lower_bound and CPE_head_difference_upper_bound to control_point_event, or add a separate control_point_difference_event table that references two control point rows.
  • Import pipeline: parse difference constraint rows from the .mps file and populate the new columns, linking each row to its two control points via the existing CP_layer1/2 pairs.
  • Solver (src/RunAuctionModule.py): for each difference constraint row, compute the combined response coefficient (Fiku − Fjku) for each well and period, and add the corresponding LP row. The solver must distinguish these rows from single-point bounds.
  • Results display: report the dual price (dL or dU) and slack for each active difference constraint on the CatchmentPage.
