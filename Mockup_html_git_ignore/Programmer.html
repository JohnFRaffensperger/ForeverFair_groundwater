Forever Fair Programmer's page

The software architecture for web routes and pages is the FastAPI app in src/web/ForeverFairPages.py. SQLite data persistence and most database access methods are in src/ForeverFairData.py. The sqlite3 transactions commit only after each stage succeeds. Repeated imports of the same case don't hurt anything. The linear programming optimization model is built and solved in src/AuctionController.py, with bid handling in src/BiddingController.py.

Demo-only authentication notice: this research demo is intentionally not production-secure. Trader access is selected from a list (or via super-login buttons on the Researcher page), and administrator pages are not protected by per-user passwords. Do not deploy this as-is on a public network. For production requirements, see Security hardening for production deployment in the Database documentation.

Installing the necessary Python libraries

1. From the workspace root (folder ForeverFair2026), first install all dependencies with the command below. That will install FastAPI, Uvicorn, Jinja2, PuLP, Pydantic, Python-multipart, pytest, and httpx from the project's pyproject.toml:

pip install -e ".[dev]"

2. To start the development server after installation, run:

python -m uvicorn src.web.ForeverFairPages:app --reload

2a. Before starting the server, create a file named .env in the project root folder (this file is gitignored and stays on your machine only). It tells the server which catchment to use:

FOREVER_FAIR_CATCHMENT=Tianqiao

Replace Tianqiao with the name of your catchment subdirectory under Catchment_data/. The server will not start if this variable is missing or names a directory that does not exist. A template is provided in .env.example.

3. Open your browser to http://127.0.0.1:8000/.

4. Your hydrologist should run the hydrology model through USGS GWM Groundwater Management Process or similar to export a linear program, with decvar, hedcon, and mps files. This code here reads those files to get the response matrix, the number of wells, the number of control points, and the number of time periods. In principle, then, this code will work with any groundwater model that works with GWM. Buttons below allow you to import these files.

Open-source desktop tools

1. Linear programming model .lpt files: Forever Fair writes auction models as .lpt files in Auction_lpt_files/. You can open, edit, and solve these files with the open-source LP Solve IDE.

2. Database files: Forever Fair uses SQLite databases (for example, Catchment_data/Tianqiao/foreverfair.db). You can open and edit these files with the open-source DB Browser for SQLite.

3. Get a background image for your SVG file from openstreetmap.org and the latitude/longitude bounding box, like this:
https://render.openstreetmap.org/cgi-bin/export?bbox=111.082318,39.039026,111.188053,39.199327&scale=100000&format=png

Running the code

  1. Load setup files below on this Programmer page. Import .decvar, .hedcon, trader names, trader wells, response matrix and bounds from .mps, and a file mapping traders to wells. Verify database status below.
  2. Enter bids from the Trader login page (or use super-login buttons on the Researcher page), then submit bids for each trader well and period. Or do nothing and let the code create automatic bids.
  3. Check the Auction manager page. Confirm close date, pumping schedule, and rights-policy settings. Then run the auction. Review outcomes on Catchment view and trader pages.
  4. Check or update head assumptions on the Hydrologist page (for example, upload revised head limits or test a synthetic head update).

Quick case setup: Tianqiao is a realistic catchment dataset. Tiny_demonstration is a small test dataset for fast checks. To set up either one quickly and avoid the Programmer.html page, you can edit src/SetupForeverFairDB.py, toward the bottom of that file. In the if __name__ == "__main__" block, call either setup_tianqiao() or setup_tiny_demonstration(). Then set FOREVER_FAIR_CATCHMENT in .env to the same case name and run the script once to rebuild that case database.

2. Import .decvar file

Forever Fair uses this data for the list of wells. A GWM .decvar file defines decision variables as "wellNNNN NC LAYER ROW COL FTYPE FSTAT stress_period". The layer, row, and col fields are the MODFLOW grid coordinates. Function SetupForeverFairDB.import_decvar stores this data in table wells with one well row per unique well number. (Confusingly, GWM writes wellNNNN as a single running index over the Cartesian product of wells and pump periods. So one index NNNN encodes well number and time period. The SetupForeverFairDB.import_decvar importer unpacks that encoding and inserts only one row per unique well number with name generated as Well {well_num}.)

3. Import .hedcon file

Forever Fair uses this information for the list of control points and head constraints by time periods. A GWM .hedcon file lists head constraints (bonNNNN LAYER ROW COL SENSE RHS_head stress_period). The RHS value is important: it is the groundwater-head constraint target for that control point and stress period, i.e., the water table must stay above RHS m. Function SetupForeverFairDB.import_hedcon creates one control-point row per unique control-point number in table control_points. The function also stages per-period minimum heads from RHS_head in table control_point_events (auction_id=0 with temporary period keys). These defaults are used by the optimizer whenever no auction-specific bounds have been applied via the Hydrologist maintenance page. (Like the wellNNNN formatting in the decvar file, GWM formats control-point tokens in the hedcon file as bonNNNN.)

4. Import trader names

Upload a tab-delimited file with columns full_name, trader_first_name, and trader_last_name. The import derives trader_id, name, and trader_loginid from the last name. A trader name can appear only once. If the same last name appears more than once in the file, a numeric suffix is appended to each duplicate (e.g. Chunmiao, Chunmiao1, Chunmiao2). Note that a trader can have more than one well.

5. Import trader-well assignments

Upload a tab-delimited file with columns name and well_id. Requirements:

  • Check 1: name must exactly match a value in the traders.name_tag column (case-sensitive). A trader may have more than one well; each well can be assigned to only one trader.
  • Check 2: well_id must exactly match a value in the wells.well_id column.

Rows that fail either check are skipped and listed in the notice. For each matched row, the import updates wells.trader_id.

6. Import well latitude and longitude

Upload a tab-delimited file with columns well_id, latitude, and longitude. The latitude and longitude are used only for the catchment visualizations.

7. Import control point latitude and longitude

Upload a tab-delimited file with columns control_point_id, latitude, and longitude. The latitude and longitude are used only for the catchment visualizations.

8. Import mps file

Forever Fair gets the groundwater response matrix and license-by-period values from this file. The GWM mps file contains the response matrix (COLUMNS section), head-constraint right-hand sides (RHS section), and well licenses (BOUNDS section). This code writes to tables response_matrix, control_point_events, and well_license. (Like the decvar and hedcon files, GWM formats control points indices with a single running index over the Cartesian product of wells and pump periods. So one index NNNN encodes control point number and time period. The SetupForeverFairDB.import_mps parser unpacks that encoding and writes response rows and period-indexed constraints.) Caution, import may be slow because these can be big files.

9. Rights policy

With the users-pay policy, traders pay for all water. They have initial quota of zero. In the first auction, traders can buy quota to plan the whole season. After the first auction, that quota is their initial rights.

With the auction-manager-pay policy, traders' initial license is firm even if the catchment is over-allocated. In the first auction, traders buy or sell quota to plan the whole season. If the catchment is over-allocated, the auction manager must pay traders for the quota they have sold to satisfy the environmental constraints. After the first auction, that quota is their initial rights, and subsequent auctions should be revenue neutral. If the hydrologist uploads new aquifer head limits, the auction manager scales quota to the environmental constraints without compensating traders for lost quota.

With the quota-scaled policy, the auction manager scales initial quota so the auction is revenue neutral. The auction manager does not compensate traders for lost quota if the catchment is over-allocated.
